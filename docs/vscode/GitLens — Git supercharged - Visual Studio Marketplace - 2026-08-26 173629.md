## GitLens——让 VS Code 中的 Git 功能更加强大

> 能够理解任何一段代码，随时可以查看所有的分支、工作树以及编码代理，同时还能在不需要离开 VS Code 的情况下，生成简洁的版本历史记录。

GitLens 是一个开源扩展程序，由 GitKraken 团队构建并维护，已安装次数超过 5100 万次。

你的代码仓库的运作速度比以往更快了。编码代理会打开分支，工作树会不断积累，拉取请求也会堆积起来——而此时你还在阅读差异信息。GitLens 将所有这些内容整合到一个交互式的视图中：包括历史记录、当前正在进行的修改、分支、工作树以及代理活动的实时状态。这样就能帮助你审查代码、进行重新合并操作，并将其整理成人们真正能够理解的提交格式。

## 入门指南

1. 安装它吧——在 VS Code 的扩展面板中搜索“GitLens”来进行安装。
2. 登录——拥有一个免费的 GitKraken 账户后，你就可以在公共仓库中查看提交图了。如果你希望在所有地方都能使用此功能，也可以开始试用吧。
3. 打开提交图表——点击活动栏中的 GitLens 图标，就会出现：你的历史记录、正在进行的修改内容，以及所有处于处理中的操作。 （ `GitLens: Show Commit Graph` 也适用。）
4. 将你使用的工具连接起来——你的 Git 主机、用于跟踪拉取请求、问题和自动链接的问题跟踪工具，以及用于跟踪会话记录和执行 GitKraken MCP 操作的编码代理。

💡 想要先体验新功能吗？请在 VS Code 的 GitLens 扩展页面中点击 `Switch to Pre-Release Version` 。

`Preview` 功能需要拥有一个免费的 GitKraken 账户，未来可能会发展为专业功能。 `Experimental` 功能目前是默认可用的，但情况会不断变化。

## 将一切集中在一个地方——使用 Commit Graph

回答“当前这个仓库到底发生了什么？”这个问题通常需要同时查看各个分支的情况、存储库中的内容、终端的状态，以及浏览器中的拉取请求信息。Commit Graph 则能在一个地方提供所有相关信息，并让你能够根据这些信息进行相应的操作。了解更多详情。

- 每一行都显示实时状态——包括是否在前、是否未被推送、尺寸是否改变，以及车道情况等等。这些信息都可以直接忽略不计。
- 你们那些尚未投入实际工作的代码，在历史记录中表现为每个工作树中的一个条目。现在，可以将它们提交到 Compose Commit 中吧。
- 执行以下操作：分支、合并、重新生成分支历史、选择性合并、撤销更改、存储更改到仓库、推送代码、拉取代码、打开拉取请求等。
- 所有细节都已准备就绪——提交、分支、存储位置、拉取请求、比较操作等。这些元素都排列成不同的表格形式； `Esc` 则处于备用状态。
- 侧边栏中的整个回购操作界面——包括概述、代理、拉取请求、工作树、分支、远程存储位置、存储库、标签等模块。点击其中一个模块可以查看相应的图表。
- 搜索那些使用 Git 进行操作的命令——比如 `message:` 、 `author:` 、 `file:` 、 `change:` ，或者简单描述一下你想要的搜索方式。
- 始终清楚自己的位置——可以前往 `HEAD` 、上游节点或合并目标。 `/` 可以检测任何分支；所有操作都由键盘控制。

## 缩小视野，发现其中的规律——可视化展示

我应该去问谁关于这个文件的问题呢？所有的变更记录都在哪里？那个代理到底处理了哪些事务呢？简单的提交列表是无法揭示所有信息的。

- 视觉历史——一个展示文件或仓库如何发展的时间线：哪些更改何时生效，这些更改的规模如何，又是谁做出了这些更改。这对于确定某件事发生的具体时刻，或者寻找相关责任人非常有帮助。
- **文件树图** `Experimental` ——将仓库中的文件按类型分组显示，每种类型对应的文件以不同的颜色表示。可以放大查看某个文件夹内实际包含哪些文件。
- **Commits Treemap** `Experimental` ——同一个图表，不同区域的变化程度用颜色来表示。
- **代理活动树状图** `Experimental` ——同样的地图，实时显示：当前有哪些代理正在阅读或编辑内容，随着他们的移动，数据也会逐渐更新。

可以通过“提交图”或“可视化历史”功能来打开这些文件，使用 `Show Visual History` 标识即可。

## 并行工作——工作树与代理

如果你频繁切换分支进行存储操作，就会失去自己的位置。一个代理可能正在其他地方工作，而你无法知道它是否正常运行、遇到了问题还是正在等待你的指令。随着工作地点越来越多，这种情况会变得更糟。

## 在不失去节奏的情况下完成工作

工作树是指同一仓库的另一种版本——这是一个可以保持开放的分支，无需进行任何存储操作。GitLens 负责处理与这个分支相关的所有操作。

- 可以从某个分支、某个提交或某个拉取请求中创建一个新文件，然后打开这个窗口或一个新的窗口来查看它。
- 每个工作树在提交图中都会有一行记录，这样你就可以在不打开文件的情况下看出哪些部分是脏的。
- 将工作移接到其他节点上——将你的修改复制过去，或者将代码库中的内容应用到另一个工作树中。
- 打开一个终端窗口，将其显示在文件管理器中，或者完成后将其删除即可。

## 了解你的代理人都在做什么

- 代理会话——Claude Code 的会话会在提交图中以实时状态显示：处于活动状态、空闲状态，或者需要输入数据。可以从当前处于活动状态的会话中直接恢复执行。
- 开始与代理协作——选择一个问题，然后 GitLens 会创建相应的分支或工作树，并将其交给编码代理进行处理。
- **Kanban 代理** `Experimental` ——将图表转换为板状视图，根据哪些需求最急需处理来分组代理会话。
- 在终端中，你的代理会打印出分支、标签或范围的哈希值。点击这个哈希值后，它就会出现在提交图中。
- GitKraken MCP——为你的编程工具提供对 Git 历史记录、拉取请求和问题的结构化访问。可以将它安装在 Claude Code、Codex、Gemini CLI、GitHub Copilot CLI、OpenCode 中，或者嵌入到你的集成开发环境中的聊天功能中。

## 继续推进 pull 请求的工作吧。

拉取请求就是任务等待被处理的地方。GitLens 将整个流程都集成到了编辑器之中：开始工作功能可以将问题转化为分支或工作树结构；Launchpad 则能够跟踪任务的进展；而您无需离开图表界面即可进行审批和确认任务。

## 启动平台——整理那些等待您的任务吧。

评审过程不应在编辑器、GitHub 和收件箱之间来回切换。Launchpad 将你参与的每个 pull 请求整理在一个列表中，并按照实际阻碍进度的情况进行排序。你可以直接查看某个请求，或者直接使用编程助手开始评审流程，而无需打开多个标签页。了解更多详情。

## 打开、审查，然后直接合并即可。

在 Graph 的“拉取请求”面板中，可以直接打开这些拉取请求。最新的更新会首先显示出来，并且会使用与 Launchpad 相同的标识来进行标记——包括可合并、被阻止、需要审核、需要跟进等状态。选择某个拉取请求后，其详细信息就会立即弹出来。

- 在这里进行审核——可以对比差异，或者将整个文件交给编码代理来审核……
- 继续处理这个任务吧——切换到该分支，在工作树中打开它。或者，如果还没有远程版本，就下载该分支的远程版本。
- 通过确认操作的分割按钮来实现合并、合并重排或重新调整分支。
- 堆叠的拉取请求——GitHub 上的这些堆叠请求被分组显示在面板中，每个层的位置通过相关的参考标签进行标识。聚焦任何一个层即可将图表的范围缩小到整个堆叠请求中；而合并操作则通过 GitHub 的堆叠感知合并功能来实现，这会显示有多少拉取请求会被合并。

## 完成与合并之间的时间间隔缩短——人工智能在编译和重新基于分支操作方面的表现

真正有效的代码并不是那些已经合并进仓库的代码。在合并过程中，会有一些难以理解的提交内容需要处理，还需要编写一些说明性的文字，还要进行多次评审工作。此外，还有那个让人头疼的下午，因为重新合并代码而浪费了时间。所有这些事情都大大缩短了完成项目所需的时间。

- 在提交 Pull 请求之前，先进行审查工作——全面审视你的变更内容，而不是逐文件进行检查。将审查结果提交给编码助手，由他们来负责实施相应的修复措施。
- 合并提交——你在十几个文件中修改了三十个项目，这些修改拼凑在一起时显得很杂乱。而“合并提交”则会将它们分别整理成独立的提交，每個提交只负责处理一项任务。对于已经提交到分支中的更改，同样可以执行“合并提交”操作。
- 请解释这些更改——用简单的语言说明每次提交、存储库、分支，或者您自己所做的更改究竟实现了什么效果。
- 生成提交信息——同时保留那些被修改的内容的注释，以及基于实际变更而编写的拉取请求标题和描述。而不是从空白模板中直接生成这些内容。
- 生成变更日志——为某个分支、某个标签，或者你已对比过的任何一系列提交记录提供发布说明。

## 无需恐惧的重新基准化

将回放操作重新执行，可以将你的提交操作重置到一个新的起点。而重新排列这些回放操作则相对简单。不过，真正让人头疼的是那些冲突点——这些冲突点就是导致分支停滞一周的原因。

交互式重新分支编辑器允许你拖动提交进行重新排序，或者标记某些提交以便合并、重新命名或删除。在重新整理过程中，它会自动找出会产生冲突的提交，并在执行任何操作之前向你发出警告。之后，它会将所有有冲突的文件集中显示在一个面板中，让你能够看到双方的版本差异。

自动重新合并功能会为您完成所有操作。它会自动执行重新合并过程，通过人工智能来解决每一处冲突，并让您知道系统做出了什么决定以及其决策的有信度如何——当系统不确定时，它会暂停操作。如果您不喜欢最终的结果，只需撤销一次操作，您的分支就会恢复到原来的状态。

## 集成/整合

无论你托管了什么内容，以及处理了哪些问题，GitLens 很可能会识别这些内容——并且会将那些拉取请求和问题添加到你的历史记录中。

自动链接功能可以在 GitHub、GitLab、Jira、Gitea、Gerrit、Google Source、Bitbucket、Bitbucket Server、Azure DevOps 以及自定义服务器上使用。对于由用户自行管理的版本，如 GitHub Enterprise 和 GitLab Self-Managed 版本，则需要使用高级功能。该工具与 GitHub、GitLab 和 Jira 的集成非常完善，能够显示自动链接的详细信息，同时还能展示拉取请求、分支和提交之间的关联关系，以及用户头像信息。

在了一个非典型的域名上吗？可以添加一个自定义的远程服务器，将其映射到内置的服务提供者上，或者教给 GitLens 一个它不知道的服务。你还可以定义自己的自动链接，比如指向 Jira 上的问题或 Zendesk 上的工单。

## blame、Hovers 以及 CodeLens

GitLens 之所以能够赢得声誉，是因为它始终坚持了以下原则：免费、保持原样，并且默认情况下都是如此。

- 在行号和状态栏中显示责任归属信息——这种方式非常隐蔽，可以在当前行的末尾以及状态栏中逐行显示每个操作的责任者。
- Rich 悬停在某个项目上时，会显示关于该项目的责任注释、关联的问题以及快速操作选项。
- Git 代码提示功能——在每個文件的顶部以及每个代码块中，都会显示最近的操作记录和作者信息摘要。
- 文件注释功能——可以对整个文件进行责任分配、查看最近的操作记录，还可以查看热图信息，所有这些功能都可以在编辑器界面直接查看。
- 修订导航——可以一步到位地查看文件的修改历史，通过点击进行回顾或前进。
- 文件历史和行历史——能够追踪整个文件或单行的在改名和合并过程中的变化。
- Git 命令面板——一种循序渐进的方式，无需记忆即可执行 Git 命令。此外，还能快速访问分支和文件历史记录、提交搜索、存储点以及仓库状态。

💡 不是适合你的吗？所有的注释都是可以自定义的，而 `Toggle Line Blame` 和 `Toggle Git CodeLens` 则可以关闭这些功能。详细的设置列表可以在帮助中心中找到。

## 浏览并对比各种选项——侧边栏视图

你的仓库中的每个部分都有各自的视图，这些视图既可以作为列表来使用，也可以作为单独的视图呈现。大多数工具都使用了类似“GitLens”的标签式视图在版本控制中展示内容，这样它们就可以轻松区分开来，而不需要面对八个折叠的标题所带来的空间竞争问题。

- 提交项、分支、远程存储、存储位置、标签、工作树以及贡献者——你可以浏览这些选项中的任何一个，并根据自己的需要进行操作：查看、比较、存储、创建工作树、了解谁写了哪些内容。
- 搜索与比较——可以搜索历史记录，或者比较任意两个分支、标签或提交内容。这些结果可以长期保留，随时可供参考。
- 检查并创建拉取请求——对于您所选的内容，请查看完整的详细信息；对于您所在的分支，请查看相关的拉取请求信息。
- 存储库——都是一样的，按照存储库进行分组，适用于多根工作区的情况。

💡 “分离视图”功能可以独立地打开一个标签页；“分离所有视图”功能则会将所有标签页分开显示；“设置为主视图”功能则可以指定哪个标签页会优先打开。 `Reset Views Layout` 功能则可以将所有标签页恢复到原来的状态。
